# School construction projects, requests, and M-Pesa donations

Status: ready-for-agent
Type: feature
Base branch: v3

## Problem Statement

Visit Nyumba currently introduces Sahajanand Special School, Galana Farm, and Kibarani Feeding Center and lets visitors register visits. It does not show the classrooms and school walls Nyumba has built, or give people a way to request similar support for their schools. Staff need every submitted request available in the existing admin area, with an email notification to the designated recipient.

People also need to understand that visiting any of the three destinations is already enough of a contribution. Those who still want to give money need an optional M-Pesa donation route, including a payment QR code. Staff need payments automatically recorded and visible in admin, without mistaking an intention to donate or an unverified report for money received.

## Solution

Add two public sections to the v3 website: **Schools we have helped**, featuring completed classrooms and school walls with a school construction request form, and **Support Nyumba**, offering optional M-Pesa donations. Retain the existing visual identity and visit booking journey.

Lead the donation section with: “Your visit to Sahajanand Special School, Galana Farm, or Kibarani Feeding Center is already enough of a contribution. If you would still like to give, you can make an optional donation through M-Pesa.” No donation is required to book, visit, or submit a school request.

Extend the existing authenticated admin area with school requests and donation records. Persist school requests and notification jobs reliably; automatically receive, verify, and deduplicate M-Pesa transaction notifications. Show a scannable M-Pesa payment QR code and readable merchant payment instructions. Keep unknown or unmatched payment outcomes explicit until they can be resolved.

## User Stories

1. As a visitor, I want to find a section about Nyumba's school construction work, so that I can understand its educational contribution.
2. As a visitor, I want to see completed classrooms, so that I can see what Nyumba has built so far.
3. As a visitor, I want to see completed school walls, so that I can understand that this support is also available.
4. As a visitor, I want project photographs, school names, locations, and short descriptions, so that the work has concrete context.
5. As a visitor, I want dates and quantities shown only when verified, so that I can trust the impact claims.
6. As a visitor using a phone or keyboard, I want accessible project images and navigation, so that I can explore the section easily.
7. As someone requesting support for a school, I want to submit a request without an account or booking, so that I can explain the school's needs directly.
8. As a requester, I want to request a classroom, a school wall, or both, so that I can describe the relevant support.
9. As a requester, I want to provide my name, relationship to the school, phone, and email, so that Nyumba can follow up.
10. As a requester, I want to identify the school and its location, so that the team can evaluate where support is needed.
11. As a requester, I want to explain the need and desired scope, so that the team can understand the request.
12. As a requester, I want clear required fields and correctable errors, so that I can submit accurate information.
13. As a requester, I want valid input preserved after an error, so that I do not have to start again.
14. As a requester, I want a saved-request confirmation and reference, so that I know my submission was received.
15. As a requester, I want clear wording that submission does not guarantee construction, so that I understand the next step.
16. As a requester, I want refreshes and repeated clicks to avoid duplicate submissions, so that the team receives one request.
17. As a requester, I want my contact details and request kept private, so that only authorized staff can review them.
18. As the designated staff recipient, I want an email for each new school request, so that I know when someone needs follow-up.
19. As the designated staff recipient, I want the email to include the request reference, relevant details, and an admin link, so that I can review it efficiently.
20. As an administrator, I want a school requests list within the existing admin, so that I can use the same login.
21. As an administrator, I want to search and filter requests, so that I can locate a particular school or type of support.
22. As an administrator, I want to open every submitted field and its submission time, so that I can assess the full request.
23. As an administrator, I want to see notification delivery state, so that I can identify requests whose email needs attention.
24. As a visitor, I want to hear that my visit is enough of a contribution, so that I do not feel obliged to give money.
25. As a visitor, I want to donate without booking a visit, so that I can support Nyumba independently.
26. As a donor, I want to choose a positive donation amount in Kenyan shillings, so that I can give an amount I am comfortable with.
27. As a donor, I want the approved merchant name and Paybill or Till details, so that I can verify the recipient before paying.
28. As a donor, I want a scannable M-Pesa payment QR code, so that I can initiate payment conveniently.
29. As a donor using one phone, I want readable payment instructions and a copyable reference when applicable, so that donating does not depend on scanning my own screen.
30. As a donor, I want to authorize payment in M-Pesa, so that I never enter my M-Pesa PIN on the website.
31. As a donor, I want the website to distinguish awaiting payment from confirmed receipt, so that I know whether money has been recorded.
32. As a donor, I want clear guidance when a QR code cannot be generated or payment confirmation is delayed, so that I can avoid accidental repeat payments.
33. As an administrator, I want eligible payments received through QR and direct merchant payment instructions recorded automatically, so that I do not transcribe receipts.
34. As an administrator, I want duplicate notifications to produce one transaction record and one contribution to totals, so that the ledger stays accurate.
35. As an administrator, I want to see the receipt, amount, transaction time, reference, and available payer information, so that I can trace a donation.
36. As an administrator, I want to distinguish donation attempts, verified donations, and unmatched or unverified receipts, so that intentions and uncertainties do not inflate donation totals.
37. As an administrator, I want donation search, date filters, state filters, and pagination, so that the records remain usable as volume grows.
38. As an administrator, I want verified donation counts and totals for the selected filters, so that I can understand recorded contributions.
39. As an administrator, I want delayed and conflicting payment information surfaced for review, so that missing confirmation is not silently treated as failure or success.
40. As an operator, I want private configuration for notification recipients and M-Pesa merchant credentials, so that operational settings do not leak into public assets.
41. As an operator, I want retries and recovery procedures for notifications and payments, so that temporary outages do not silently lose records.
42. As an existing visitor or administrator, I want bookings, overnight requests, transport choices, feedback, and their notifications to keep working, so that the new sections do not disrupt existing services.

## Implementation Decisions

- **Scope and branch:** implement on top of `v3`. This spec is the current deliverable; it does not implement or deploy the feature. Do not propagate implementation to other version branches as part of this request.
- **Confirmed versus proposed:** the two sections, completed-project showcase, school request form, admin visibility, staff email notification, optional donations, automated M-Pesa recording, and payment QR are user requirements. Field choices, list filters, placement, and technical behavior below are proposed implementation defaults synthesized from the repository. The testing approach has been explicitly confirmed by the user.
- **Architecture:** extend the existing server-rendered PHP application, private SQLite database, migrations, public form handling, and admin authentication. Introduce separate school-request and donation domain modules rather than representing either as bookings. Reuse common validation, escaping, phone normalization, email presentation, and provider-client conventions where appropriate. No new frontend framework or public administration API is needed.
- **Public composition:** place the school-project section after the destination stories and before planning; place the donation section after planning and before the final visit call to action. Add responsive navigation anchors for both. Match v3 typography, colors, imagery, and keyboard behavior. School construction is not a fourth bookable destination. Keep the three destination booking controls readily available.
- **Project showcase:** use a structured, maintainable content collection containing a stable project identifier, school name, location, construction type, description, photographs with alternative text, and optional verified completion date and quantities. Only publish owner-approved completed projects. Preserve supplied originals and existing photo privacy treatment; optimize public copies. Do not relabel existing Sahajanand classroom photos as evidence of construction at other schools. Do not invent projects, numbers, dates, or documentary photographs. If assets are missing, use an honest empty state during development and record content readiness as a launch dependency. A project-content editor in admin is not part of this first version.
- **Request fields:** require contact name, relationship to the school, valid email, normalized phone, school name, county, town/locality, support type (`classroom`, `school_wall`, or `both`), and a description of the need. Suggested bounds are 120 characters for names and relationship, 180 for school name, 120 each for county/locality, 254 for email, and 3,000 for the description. Explain that only contact and school information needed for follow-up should be supplied. Do not request pupil names, IDs, or files.
- **Submission contract:** provide a dedicated school-request POST action, independent of booking submission. Apply server-side validation, CSRF protection, bounded request size, a session submission token, and server-side throttling using the application's trusted-proxy policy. Invalid input returns field errors with preserved values. Save a random reference, normalized fields, submission-token digest, and creation timestamp. A repeat submission token returns the original saved result. Redirect after successful persistence; do not show success when storage fails. Confirmation is session-bound and says the request was received for consideration, not approved.
- **School notification:** use a dedicated configurable recipient or recipient list. Do not silently adopt destination contacts or the current booking-manager override. Save a durable notification job in the same transaction as the school request, with a stable idempotency key. Include the request reference, school, support type, contact and need details, and an authenticated admin link in HTML and plain text. Use the existing Resend client and email design. Escape submitted content; never use it directly as mail headers.
- **Queue integration:** the current email queue is tied to booking identifiers and booking/feedback message kinds. Adapt its schema and worker deliberately to support school requests, or introduce a separate outbox using the same delivery mechanism; do not create dummy bookings or bypass the queue. Preserve existing queued payloads and idempotency keys. Record requests even when delivery is temporarily unconfigured, retain pending notification intent, and show a configuration-required state in admin. Retry provider outages with the existing lease and bounded idempotency-window pattern; send failures must not remove a saved request. Distinguish provider acceptance from confirmed inbox delivery. Automatic requester acknowledgement email is not required.
- **School request admin:** add a protected navigation entry, list, and detail view. Use newest-submission-first ordering and 25-row pagination. Search request reference and school/contact name; filter support type and submission date range. Details show all submitted fields, reference, timestamp, and notification state. No approval, rejection, or construction scheduling workflow is implied by viewing a request.
- **Merchant configuration:** require owner-supplied Paybill/Till, merchant display name, merchant type, and any account/reference convention. Keep Daraja credentials and environment selection server-side. An ordinary contact phone number is not evidence of a usable merchant integration. If the supplied payment arrangement cannot support automated callbacks and payment QR generation, leave collection unavailable and document the required merchant onboarding; never substitute another recipient or mark a manual payment claim as received.
- **Payment approach:** use Safaricom Daraja for merchant payment notifications and a supported payment QR flow. C2B notifications cover payments to enabled Paybill/Till merchants; a QR is an initiation mechanism and is not proof of payment. Verify the selected merchant's supported QR transaction type, amount/reference fields, and callback setup against its current Daraja contract before implementation is finalized. Safaricom documents these capabilities in its [C2B documentation](https://developer.safaricom.co.ke/apis/CustomerToBusiness) and [API catalogue](https://developer.safaricom.co.ke/apis).
- **Donation initiation:** accept a positive KES amount in whole shillings within configured merchant/provider limits. Store money using exact integer units, never floating point. Persist a local donation attempt and non-guessable reference before calling the QR provider. Show the returned, validated payment QR with its merchant name, amount, and reference, plus Paybill/Till instructions. Use CSRF and submission idempotency for the initiation POST, rate limits, network timeouts, and safe retry behavior. Do not require a donor account, booking, school request, phone number, or email just to display payment instructions. Payment authorization stays in M-Pesa.
- **QR behavior:** generate the actual provider-supported merchant payment payload, not a QR that merely points to the homepage. Support scan-friendly contrast, clear space, and an accessible text alternative. If the merchant requires an amount before generating a dynamic QR, show the amount form first. Surface QR expiry only when supported by the provider contract. QR generation failure leaves the attempt unconfirmed and allows safe retry; it never displays a paid receipt. Same-device users can use the displayed payment details without scanning. STK Push is not required for this scope.
- **Payment records:** introduce donation attempts, merchant transaction records, and durable payment-event processing records. Attempts retain reference, expected amount, creation time, provider request identifiers where available, and initiation outcome. Transactions retain unique provider receipt scoped to environment/merchant, actual amount, currency, merchant identifier, provider transaction time, received time, provider reference, available payer identity, verification state, and optional matched attempt. Keep attempt state separate from actual receipt state: a completed QR request is not a completed donation. Payer fields may be missing or hashed; do not promise full phone/name availability.
- **Callbacks:** provide dedicated HTTPS server endpoints for the enabled merchant's confirmation and related asynchronous results. These endpoints do not rely on browser sessions or CSRF tokens. Validate content type, body size, schema, merchant, receipt, amount, and timestamps; use provider-supported source controls at the trusted ingress. Do not invent an unsupported webhook signature contract. Persist accepted events durably before acknowledging according to the provider contract, then process idempotently. Reject malformed or wrong-merchant events without creating a verified donation. If authenticity cannot be established from the configured callback path, retain an unverified event and require an authenticated provider query or verified merchant reconciliation before counting it.
- **Matching and totals:** match transactions by supported stable provider/account references. Never guess a match from amount alone. For a dedicated donation merchant, verified direct payments without a website attempt are still donations. For a merchant shared with other activities, use an approved donation reference convention where supported and keep payments without sufficient attribution in a separate unmatched queue. Display them for review but exclude them from donation totals. A mismatched amount remains a real receipt if verified; flag the mismatch and record the actual amount without falsely confirming the original attempt. A duplicate receipt cannot add a second transaction or increment a total. Conflicting duplicate payloads require review and must not overwrite verified facts.
- **Late outcomes and recovery:** process callbacks independently of whether the donor keeps the page open. Allow a delayed verified payment to resolve an awaiting/review attempt without charging again. A missing callback or abandoned page is an unknown outcome, not proof of failure. Use scheduled retries and reconciliation for known provider identifiers; do not initiate another payment during recovery. Safaricom's [Transaction Status API](https://developer.safaricom.co.ke/apis/TransactionStatus) requires a receipt or originator identifier, so it cannot discover arbitrary missing transactions. Provide an operator procedure to compare merchant statements and recover missed receipts through a verified, idempotent backend reconciliation path. Record evidence and actor/source for reconciled updates. Document any gaps requiring merchant support; do not claim a complete ledger solely from callback delivery.
- **Public payment status:** expose only the current session's donation attempt or an opaque status capability. Show awaiting confirmation, confirmed received, QR-generation failure, or needs-review guidance based on persisted evidence. Confirmation may show the amount and reference with masked payer information. Never offer public receipt/name/phone enumeration or treat a user-entered receipt as authoritative. Preserve normal booking and school-request availability during payment outages.
- **Donation admin:** add a protected list and detail views for attempts and received transactions, with clear separation between verified donations and unverified/unmatched records. Search local reference and provider receipt; filter state and inclusive transaction/submission dates as labelled. Use stable newest-first order and pagination. Show actual amount, KES currency, provider receipt, references, merchant, available payer details, timestamps, match state, verification state, and concise processing history. Totals apply to the selected filters and include only verified, attributable donations. Preserve evidenced reversals as linked adjustments and exclude reversed amounts from net totals; initiating refunds or reversals is outside scope.
- **Privacy and operations:** apply existing login, session expiry, credential rotation, escaping, parameterized queries, and no-store behavior to every new admin route. Keep sensitive payloads, credentials, and donor/requester details out of public assets and routine logs. Persist timestamps consistently and display them in Africa/Nairobi. Provide deployment configuration, worker schedules, callback registration, queue/reconciliation monitoring, and recovery documentation. Static previews may show layouts and clearly labelled sample content but cannot collect requests or payments.
- **Migrations and compatibility:** use repeatable, additive migrations and appropriate uniqueness constraints and indexes. Preserve bookings, feedback, sessions, and queued email/SMS state. Migration and runtime failures must not issue false confirmations. Extend the existing test runner with the new behavioral coverage.

## Testing Decisions

- **User-confirmed seam:** exercise the public forms and admin through the real PHP application with temporary SQLite and session storage; mock email and M-Pesa at the provider boundary; verify the QR/payment flow in Safaricom's sandbox before launch. The user explicitly answered “Yes, use this approach.”
- Prefer one application-level HTTP/browser seam for observable outcomes. A good test submits or receives real application requests and verifies the resulting public confirmation, authenticated admin record, or provider interaction. Do not assert private helper structure, CSS class choices, or SQL layout. Use private database inspection only for durability, uniqueness, migration preservation, and transaction atomicity that are not otherwise observable.
- Prior art exists in the booking, contacts, feedback, and admin Playwright suites: isolated PHP servers, fictional records, temporary databases, authenticated browsing, mobile viewports, and no-JavaScript runs. Reuse that setup. The existing email and feedback-worker PHP suites provide injectable sender and clock patterns for worker retry/concurrency tests. Add only the analogous provider boundary needed for deterministic M-Pesa responses; no production test-control endpoint.
- Cover approved project rendering, both construction types, missing content, accurate optional quantities, responsive navigation, keyboard access, and preservation of the three booking flows. Review desktop and mobile layouts without brittle pixel snapshots.
- Cover each request type, all required fields, valid normalization, invalid/oversized input, escaped content, CSRF and throttling, duplicate/replayed submission, confirmation after reload, and storage failure. Show that each saved request is visible only after admin login and that list filters, pagination, detail fields, and notification states are accurate. Verify core request and admin flows without JavaScript.
- Cover atomic request/outbox persistence, recipient routing, disabled/missing configuration, provider acceptance, retryable failure, worker lease contention, crash/retry with the same idempotency key, and expiry into review. Confirm that viewing admin never sends an email and that existing booking emails/SMS remain unaffected.
- Cover donation amount validation, configured and unavailable merchants, QR content/recipient/amount correctness, QR failure, text instructions, no-JavaScript fallback, duplicate initiation, and private status access. Decode generated QR fixtures to verify the actual payload, then perform a separate sandbox scan check; a displayed square image alone is not acceptance evidence.
- Submit representative provider callbacks through the actual HTTP handler. Cover verified success, duplicate/concurrent delivery, delayed and out-of-order events, malformed or forged inputs, wrong merchant/environment, unsupported payer fields, mismatched amounts, unmatched direct payments, shared-merchant attribution, persistence failure before acknowledgement, and conflicting receipts. Verify one ledger entry per receipt and that unverified, unmatched, pending, failed, and reversed amounts do not inflate net donation totals.
- Exercise reconciliation success, timeout, missing provider identifiers, and corrected late outcomes using a controlled clock and mocked provider. Assert that recovery does not initiate a second payment and that the audit history remains traceable. Test migration from a populated v3 database and rerun relevant booking, overnight, transport, feedback, admin, email, and SMS regressions.
- Routine tests must send no real emails and move no real money. Sandbox acceptance requires configured merchant/API access and evidence of a scannable supported QR, callback receipt, admin visibility, and deduplication. Where sandbox cannot reproduce a production merchant capability, record that limitation and require an explicitly authorized controlled production verification before declaring that capability operational.

## Out of Scope

- Implementing or deploying the feature during this spec-writing task; this issue authorizes the defined future implementation scope.
- Changes to v1, v2, main, or other branches as part of this request.
- School request approval/rejection workflows, construction scheduling, budgets, procurement, site inspections, or promises of eligibility or completion dates.
- Public requester accounts, pupil records, file uploads, application tracking portals, and automated requester emails or SMS.
- An admin CMS for school project photographs and copy; maintain the initial verified showcase through structured content.
- Mandatory donations, donation-based visit access, linking donations to school-request priority, fundraising targets, public donor rankings, or restricted-purpose allocation.
- STK Push, recurring donations, cards, other payment providers/currencies, tax receipts, accounting-system integration, or automated refund/reversal initiation.
- Treating browser activity, QR scans, pasted receipts, screenshots, or SMS scraping as authoritative payment confirmation.
- A blanket guarantee to discover all historical merchant transactions without provider identifiers or access to merchant reconciliation evidence.

## Further Notes

- Inspected `v3` at commit `ffecf7b`. The current application already has private SQLite persistence, authenticated read-only booking/feedback administration, Resend delivery with durable retries, and Africa's Talking booking SMS. It has no school-request or M-Pesa integration. Source behavior takes precedence over older documentation that still describes earlier optional-email behavior.
- Required launch inputs: an approved list of completed projects with school names, locations, descriptions, dates/quantities where known, photographs and publication permission; designated school-request notification recipient(s); approved M-Pesa merchant name and Paybill/Till; whether that merchant is dedicated to donations; supported account/reference convention; Daraja sandbox and production access for the required APIs; private API credentials; HTTPS callback base URL; and worker/reconciliation operation arrangements.
- The conversation did not provide a verified M-Pesa number or school notification recipient. Existing contact numbers and booking-manager addresses must not be repurposed by assumption. These are configuration/content handoffs, not reasons to fabricate data or prevent development against fixtures.
- Full QR contract details and merchant entitlement must be checked in the authenticated Daraja portal during implementation. Public documentation confirms the intended integration family but does not prove that the owner's particular account is enabled. Record onboarding or sandbox limitations as launch blockers while continuing independent implementation.
- Terminology for this effort: a **school project** is approved public evidence of completed construction; a **school request** is a private request for consideration; a **donation attempt** is an intention/payment initiation; a **merchant transaction** is a provider-reported movement of funds; a **verified donation** is a verified transaction attributable to donations. Visiting is described as a contribution in public copy, but a visit is never entered as a monetary transaction.
